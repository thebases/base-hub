# base-calendar: user and administrator guide

## 1. Purpose and audience

`base-calendar` is a generic, model-agnostic recurrence engine for calendar views. It lets any record of any registered model (for example a task, a meeting or a shift) repeat on a schedule, and it returns the calendar entries for a date range, expanding repeating rules on the fly.

| Audience | Use |
| --- | --- |
| Administrators / power users | Define and review recurrence rules and exceptions |
| Calendar view (frontend) | Reads occurrences and reschedules them by drag and drop |
| Integrators | Call the RPC/MCP tools to query or move occurrences |

## 2. Prerequisites and installation

- Depends on `base` and `base-automation`; `auto_install` is on, so it is installed automatically.
- The background cleanup job relies on the `base-automation` scheduler being active (see section 6).

## 3. Key concepts

| Concept | Plain-words meaning |
| --- | --- |
| Calendar Recurrence (`base.calendar.recurrence`) | A repeat rule attached to one master record, identified by Model plus Record ID. |
| Calendar Recurrence Exception (`base.calendar.recurrence.exception`) | A change to a single occurrence: moved to another date, or skipped. |
| Occurrence | One concrete instance generated by a rule for a date. Occurrences are calculated when read, never stored, so open-ended rules stay cheap. |

### Recurrence fields

| Field (UI label) | Meaning |
| --- | --- |
| Model (`sys_model`) | Name of the target model; must be a registered model (required) |
| Record ID | Id of the master record on that model; you must be able to read it (required) |
| Frequency | Daily, Weekly, Every 2 Weeks, Monthly, Yearly, Specific Weekday, Specific Day of Month (required) |
| Interval | Repeat every N units of the frequency, default 1 |
| By Weekday | Weekdays 0 (Sunday) to 6 (Saturday); required for Weekly, Every 2 Weeks and Specific Weekday |
| By Month Day | Day of month 1 to 31; required for Specific Day of Month; short months use their last day |
| Start Date | First active date (required) |
| End Date | Last active date; empty means it repeats indefinitely |

### Exception fields

| Field (UI label) | Meaning |
| --- | --- |
| Recurrence | The rule being overridden |
| Original Date | The generated date being overridden |
| Override Date | The new date and time; empty when skipped |
| Is Skipped | Removes this occurrence from the calendar |

## 4. Where to find it

| Menu or route | Opens |
| --- | --- |
| Admin > Calendar Recurrences ("Lặp lại lịch") at `/web/base.calendar.recurrence` | List and form of rules, with search by Model and Frequency and group-by |
| Exceptions | No menu entry; list and form views exist for the exception model and exceptions are normally created by rescheduling |

## 5. Step-by-step tasks

### Make a record repeat
1. Open **Admin > Calendar Recurrences** and click New.
2. Enter **Model** and **Record ID** of the master record.
3. Choose **Frequency** and **Interval**. For weekly-type rules fill **By Weekday**; for Specific Day of Month fill **By Month Day**.
4. Set **Start Date** and optionally **End Date** (not earlier than the start), then save.

### Stop a series
Open the rule and set **End Date**, or delete the rule.

### Skip or move one occurrence
Create an exception with the rule, the **Original Date**, and either **Is Skipped** or an **Override Date**. In a calendar view, dragging an occurrence does this for you.

### Reschedule from a calendar view (scope)
| Scope | Effect |
| --- | --- |
| this | Moves only that occurrence (an exception is written) |
| following | Ends the current rule the day before and starts a new rule from the new date |
| all | Shifts the whole rule's start date (and end date) by the same difference |

## 6. Administration and configuration

- **Access**: members of `base.group_user` have read, write, create and delete on both models. Target-record access is still checked: you cannot create a rule for a record you cannot read.
- **Company scope**: a rule takes the creator's current company; an exception inherits its rule's company.
- **Seeds**: an Automation Action "Calendar: Cleanup Orphaned Recurrences" (Go Handler `base_calendar.cleanup_orphaned_recurrences`) and an Automation Cron of the same name running every 300 seconds (max failures 5). They delete rules whose master record no longer exists or whose model is no longer registered. Manage them under **Automation > Actions / Crons**.
- Deleting a rule also removes its exceptions.

## 7. API and automation touchpoints

| Touchpoint | Purpose |
| --- | --- |
| RPC `base.calendar.recurrence` `occurrences` (`sys_model`, `date_from`, `date_to`, optional `domain`) | Plain records plus expanded recurring occurrences for the range; recurring items carry `is_recurring`, `recurrence_id`, `master_record_id`, `occurrence_date`, with id format `recurrence_id:date` |
| RPC `reschedule_occurrence` (`original_occurrence_date`, `new_datetime`, `scope`) | Move an occurrence, by rule id |
| MCP `calendar.occurrences` | Same as `occurrences` |
| MCP `calendar.reschedule_occurrence` (`recurrence_id`, `original_occurrence_date`, `new_datetime`, `scope`) | Same as the RPC |
| MCP `calendar.record.search_read`, `.read`, `.create`, `.write`, `.unlink` | CRUD on the two calendar models; `create` requires `idempotency_key` |

Dates accept `YYYY-MM-DD` or RFC3339; `date_to` is exclusive and must be after `date_from`.

## 8. Troubleshooting and FAQ

| Symptom | Cause and fix |
| --- | --- |
| "sys_model ... is not registered" | Check the model name spelling and that its module is installed |
| "permission denied: cannot create a recurrence on ..." | You lack read access to the master record |
| "frequency ... requires by_weekday / by_monthday" | Fill the weekday or month-day field for that frequency |
| "end_date must not be before start_date" | Correct the dates |
| A repeating item does not appear | The master record is deleted or unreadable to you, the rule is outside its date range, or the range requested is wrong |
| Rule disappeared | The cleanup job removed it because its master record was deleted |

## 9. Limits and notes

- Occurrences are virtual and calculated per request; nothing is pre-generated.
- Orphaned rules are hidden immediately but physically removed only at the next cleanup run (up to about 5 minutes later).
- The master record is linked by model and id only, not a database foreign key.
- The company of a rule is the creator's session company, not the master record's.
